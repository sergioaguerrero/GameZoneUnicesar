# Warranty Analysis

**1. The two warranty types share common attributes (dates, associated product) but also have different attributes and behaviors (duration, coverage, cost). How is this situation reflected in the class hierarchy design? Which object-oriented mechanism allows each warranty type to have its own duration without duplicating code?**

The situation is modeled with an **abstract superclass** `Warranty` and two concrete subclasses, `BasicWarranty` and `ExtendedWarranty`. `Warranty` (in the `model` package) contains everything that is identical for every warranty: the private attributes `warrantyId`, `product`, `sale`, `startDate` and `endDate`, their getters, and the concrete methods `isActive(LocalDate)` and `generateWarrantyCertificate()`. What changes from one type to another is declared as **abstract methods**: `getDurationInMonths()`, `getWarrantyType()` and `getAdditionalCost()`. Each subclass implements them with `@Override` (6 months / free for the basic warranty, 12 months / 10% of the product price for the extended one).

The mechanism is **inheritance combined with polymorphism** (dynamic dispatch of abstract methods). The shared code only calls `getDurationInMonths()` and never asks which subclass it is running in, so the JVM executes the version of the actual object. Because of this, the certificate, the validity check and the services work with any `Warranty`, and adding a new warranty type in the future only requires a new subclass, without touching the existing code.

**2. The business rule states that only consoles generate an automatic basic warranty, not video games. In which layer of the system is this decision located and which Java mechanism is used to check the real type of a product? Justify.**

The decision is located in the **service layer**, specifically in `SaleService` (method `applyWarranties`, called from `registerSale`). It is a business rule that depends on the content of a sale, so it does not belong to the UI (which only asks the user and displays results), to the persistence layer (which only reads and writes files), or to the model (a `Product` should not know about warranties, and `Warranty` only describes one warranty).

The real type is checked with the **`instanceof` operator** (`product instanceof Console`), because the sale items hold references of the static type `Product` and only the runtime type tells whether the product is a `Console`, a `VideoGame` or an `Accessory`. `instanceof` is preferred over comparing `getClass()` or strings because it respects inheritance and the compiler checks the type. The same check is used to validate that an extended warranty is only requested for a console that is actually part of the sale. The menu also asks about extended warranty only for consoles, but this is just a convenience: the rule is always enforced in the service.

**3. The duration of each warranty type is different (6 or 12 months). How is the expiration date calculated in each subclass? Should this calculation be done in the warranty constructor or in a separate method? Justify.**

The expiration date is not calculated inside each subclass. Each subclass only declares its duration by implementing `getDurationInMonths()` (6 or 12), and the `Warranty` constructor calculates the end date once with `startDate.plusMonths(getDurationInMonths())`. `plusMonths` handles month lengths correctly (for example, August 31 plus 6 months gives the last day of February).

The calculation is done **in the constructor** because the end date is a derived value that must always be consistent with the start date and the type: a warranty object can never exist without a valid end date, and there is no setter that could leave it outdated. It also removes the risk of forgetting to call a separate "calculate" method. The end date is not stored in `warranties.csv`; it is recalculated automatically when the warranty is loaded, so the file cannot contradict the business rule. The only precaution is that calling an overridable method from a constructor is safe here because the subclasses return **constants** (`static final`) and do not depend on instance fields that would not be initialized yet; this is documented in the JavaDoc of `Warranty`.

**4. The extended warranty adds a cost of 10% of the product price to the sale total. At which point of the sale registration flow is this additional cost calculated and applied? What modifications are necessary in the `SaleService.registerSale` method?**

The cost is calculated **after the sale has been created, the stock validated and the promotion applied, and before the sale is saved**. The service asks each `ExtendedWarranty` for its `getAdditionalCost()` (the 10% rule lives in the model, not in the service or the UI), adds all the values, and stores the result in the sale with `Sale.setExtendedWarrantyCost(...)`. The promotion discount is calculated over the items only, so the warranty cost is not discounted.

The modifications to `registerSale` were additive:
- A new overload `registerSale(customerId, sellerId, items, List<String> productIdsWithExtendedWarranty)`. If the list is `null` or empty, no extended warranty is applied. The old three-parameter method remains and delegates to the new one, so existing callers keep working.
- A validation that every id in the list is a console included in the sale.
- A call to a private method `applyWarranties`, which creates the basic warranty for each console, creates the extended one when requested, and accumulates its cost.
- `Sale` received the new attribute `extendedWarrantyCost` and the method `calculateFinalTotal()` (subtotal minus discount plus warranty cost), and the receipt now shows the warranty line. The cost is saved in `sales.csv`, so the total is still correct after reloading.
- Sales now have a unique id (`SALE-0001`, ...) generated by the service, because warranties must reference the sale they belong to.

**5. The query for "warranties expiring soon" requires iterating over all the warranties and filtering those whose end date is within the next 30 days. In which class is this method located and what dependencies does it need? Why is this location consistent with the layered architecture?**

The method `listWarrantiesExpiringSoon(int daysAhead)` is located in **`WarrantyService`** (service layer). It needs the in-memory list of warranties, which the service loads through its only injected dependency, `WarrantyRepository`, and it uses `LocalDate.now()` together with `Warranty.getEndDate()` to keep the warranties whose end date is between today and today plus `daysAhead`.

This location is consistent with the layered architecture (`ui -> service -> persistence -> model`) because filtering is a business query: the **UI** (`ConsoleMenu`) only asks the user for the number of days and prints the result, the **persistence** layer only stores and loads the data without any business criteria, and the **model** only knows the rule of a single warranty (`isActive`, `getEndDate`), not how to search among many. The service is the layer that coordinates the persisted data and the model rules. As a documented detail, `WarrantyRepository` receives `ProductService` and `SaleService` to resolve the `Product` and `Sale` references while loading (the same approach used by `ReturnRepository`), and `WarrantyService` is injected into `SaleService` through a setter to avoid a circular dependency.
